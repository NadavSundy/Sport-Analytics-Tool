# Issue #410 participant-history query-plan investigation and fix

## Status of the figures

Every number in this document is a **measured figure** under
`docs/development/reference-fixtures.md` §4.2: it was obtained from the database
or from the local API, not transcribed from a published source. No published
figure is involved and none is asserted against here. The one reference-fixture
figure quoted — BB McCullum's 116 off 56 in fixture 423788 — is cited from
`evidence/validation/423788-published-figures.md` and is unchanged by this work.

## 3. The dominant cost, by loop count

From `issue-410-plan-02-current-after-analyze.txt`, whose `Execution Time` is
889.502 ms:

```
->  GroupAggregate  (actual time=93.405..855.172 rows=51 loops=1)      <- fixture_state
      Group Key: sf_1.fixture_id
      Buffers: shared hit=806
      ->  Sort  (actual time=3.438..3.611 rows=102 loops=1)            <- input ready at 3.6 ms
      SubPlan 4
        ->  Aggregate  (actual time=11.708..11.708 rows=1 loops=51)
              ->  CTE Scan on accepted_delivery d_2
                    (actual time=5.461..11.620 rows=240 loops=51)
                    Filter: (d_2.fixture_id = sf_1.fixture_id)
                    Rows Removed by Filter: 12000
                    Buffers: shared hit=517
      SubPlan 5
        ->  CTE Scan on accepted_delivery d_3
              (actual time=2.435..2.435 rows=1 loops=102)
              Filter: (d_3.innings_id = i.innings_id)
              Rows Removed by Filter: 6060
              Buffers: shared hit=20
```

| Node                                     |   Loops |  Per loop |                               Total |
| ---------------------------------------- | ------: | --------: | ----------------------------------: |
| SubPlan 4 — `accepted_event_count`       |  **51** | 11.708 ms |                           597.11 ms |
| SubPlan 5 — `empty_standard_innings_ids` | **102** |  2.435 ms |                           248.37 ms |
| **Together**                             | **153** |           | **845.48 ms — 95.1% of 889.502 ms** |

`accepted_delivery` is referenced four times, so PostgreSQL materialises it into
a tuplestore. A tuplestore carries no index, so each correlated subquery scans
the whole set: SubPlan 4 keeps 240 rows and discards 12,000, fifty-one times;
SubPlan 5 discards about 6,060 before its first match, one hundred and two times.
That is roughly **1.24 million tuple scans to produce 51 integers and 51 arrays**.

### The buffer figures are not where the cost is, and that is the point

The whole statement reports `Buffers: shared hit=809` with no `read` at all —
about 6.6 MB, entirely cached — and the two hot subplans report only
`shared hit=517` and `shared hit=20`. There is no I/O to attribute the time to.
The cost is CPU iterating a materialised tuplestore, which `BUFFERS` does not
account for. **The attribution here rests on loop counts, not on buffers.** A
reader checking this work against the buffer numbers alone would conclude the
query is cheap.

`work_mem` was swept from 64 kB to 64 MB against the same statement — 207.5,
218.6, 139.0 and 357.6 ms at the fastest sample of five for each — with no
monotonic trend, so the tuplestore is not spilling.

### The stated hypothesis was tested and does not hold

Issue #410 proposed that the dominant cost was in **scoping** rather than
aggregation. Scoping — `selected_fixture` plus the `accepted_delivery` build —
is **41.2 ms of 889.502 ms, 4.6%**. Aggregating the participant's own figures is
about 29.2 ms, 3.3%. The dominant cost is neither: it is two correlated re-scans
of an already-scoped, already-materialised set, computing two **fixture-level
completeness fields** that reach clients only through `statisticsStatus` and
`statisticsWarnings`.

The hypothesis is recorded as disproved rather than quietly replaced.

### Why #290's improvement did not move this number

`performance-query-plans.database.test.ts` measured a hand-written fragment
covering only the `accepted_delivery` selection, and never imported
`listParticipantFixtures`. Its 34.4% improvement was real and applied to
35.9–46.5 ms of an 866–890 ms statement. The test could have stayed green
indefinitely while the endpoint stayed at 3,454 ms. Extending it to plan the
endpoint's own statement is part of this change.

## 4. The change

One CTE added; `fixture_state` rewritten as a grouped pass. Nothing else in the
statement changes.

```sql
innings_event_count AS (
  SELECT
    d.innings_id,
    COUNT(*)::int AS accepted_event_count
  FROM accepted_delivery d
  GROUP BY d.innings_id
),
fixture_state AS (
  SELECT
    sf.fixture_id,
    COUNT(i.innings_id)::int AS standard_innings_count,
    COALESCE(SUM(iec.accepted_event_count), 0)::int AS accepted_event_count,
    COALESCE(
      ARRAY_AGG(i.innings_id::text ORDER BY i.ordinal) FILTER (
        WHERE i.innings_id IS NOT NULL
          AND iec.innings_id IS NULL
      ),
      ARRAY[]::text[]
    ) AS empty_standard_innings_ids
  FROM selected_fixture sf
  LEFT JOIN innings i
    ON i.fixture_id = sf.fixture_id
   AND ${standardInningsPredicate('i')}
  LEFT JOIN innings_event_count iec
    ON iec.innings_id = i.innings_id
  GROUP BY sf.fixture_id
)
```

### Equivalence argument

1. `accepted_delivery` already restricts to non-super-over innings of the
   selected fixtures, and the existing `LEFT JOIN innings` already enumerates
   exactly those innings. Summing the per-innings counts across that join
   therefore equals the fixture-wide count the scalar subquery returned.
2. `innings_event_count` holds one row per innings that has at least one accepted
   delivery, so `iec.innings_id IS NULL` is `NOT EXISTS (...)` by construction.
3. The join is one-to-one on `innings_id`, so it introduces no row multiplication
   and `COUNT(i.innings_id)` is unchanged.
4. `SUM` over no matching row is `NULL`, not zero, where a scalar `COUNT(*)`
   subquery returns zero. `COALESCE(..., 0)` restores that, and a test covers it
   rather than leaving it to the argument. This is the one place where the two
   forms could have differed silently, and it is the reason the equivalence is
   checked by row comparison and not only reasoned about.

### The super-over exclusion, and how it survived the #285 merge

The exclusion's **meaning** is unchanged throughout; only its spelling moved.

While #285 was unmerged this statement carried the inline
`i.is_super_over = false` predicate in both `accepted_delivery` and
`fixture_state`, and deliberately did not copy
`standardInningsPredicate()` out of the unmerged branch — a fourth inline
spelling would have been the thing
`apps/backend/src/modules/statistics/super-over-scope.ts` exists to prevent.

Merging `origin/main` brought that helper in. Both call sites in this statement
now read `${standardInningsPredicate('i')}`, and **no inline
`is_super_over` spelling remains anywhere in
`apps/backend/src/modules/participants/participant.repository.ts`**, verified by
searching the resolved file rather than by assumption.

`innings_event_count` reads `accepted_delivery`, which the helper has already
restricted to standard innings, so it **inherits** the boundary rather than
restating it. It carries no `innings` alias of its own and must not acquire one.
This is recorded in the repository's own doc comment so that a later reader does
not "restore" a predicate that would be a second spelling of the same rule.

The merge conflict was in exactly this hunk: our side added the
`LEFT JOIN innings_event_count`, main's side changed the predicate spelling on
the line above it. Both were kept.

Fixture 423788's super-over assertion — BB McCullum 116 off 56, not 118 off 57 —
is green after the merge, in both
`fixture-statistics.database.test.ts` and the new
`participant-fixture-history.database.test.ts`. That is the check that the
changed spelling still governs the query it is meant to govern.

### No index was added

The expensive node is a `CTE Scan` over a tuplestore, which no index can reach.
Base-table access is already entirely index-driven — `fixture_start_date_idx`,
`fixture_squad_pkey`, `submission_pkey`, `delivery_sequence_live` — at
`shared hit=809, read=0`. An index here would have been the speculative kind the
issue forbids.

## 7. Caveats recorded rather than smoothed over

### Absolute timings are state-sensitive; only the ratio is asserted

The same unchanged statement measured **826–1016 ms** in one session and
**142–179 ms** in another after a database restart, on the same machine against
the same corpus. `issue-410-plan-02-current-after-analyze.txt` (889.502 ms) and
`issue-410-plan-07-current-fixture-state-only-second-session.txt` (350.869 ms,
for a reduced form) come from those two sessions respectively, and the per-loop
cost of SubPlan 4 differs between them — 11.708 ms against 4.759 ms.

The **ratio held in every capture: the correlated re-scans were 82–98% of
execution time throughout.** This is the most likely reason #290's machine
recorded 3,454 ms where this one records 427 ms for the same work.

Nothing in this document asserts an absolute duration as a threshold, and the
plan-regression test asserts loop counts rather than elapsed time for the same
reason.

### The cold first-call outliers are unexplained

Two large first-call observations are recorded and **not** explained:

- 9,978.5 ms — the pre-change API P95, which was the first sampled participant
  request.
- 19,199.3 ms — the first execution of the statement immediately after ingesting
  the 300-fixture corpus, against 1,088.9 ms and 826.4 ms for the second and
  third.

The cause was not isolated. Candidate explanations were considered and none was
established, so none is claimed. Both are one-off first-call effects: every
subsequent execution in both sessions, and both `EXPLAIN` captures, agree at the
steady-state figures above. This is a separate question from the one this issue
fixes, and it is not resolved by this change — the post-change run 1 P95 of
567.5 ms is the same first-call effect, now small enough to pass.

### Nearest-rank P95 at n=10 is the maximum sample

`scripts/measure-api-response-times.mjs` computes
`ordered[Math.ceil(samples * 0.95) - 1]`. At the documented ten samples that is
`ordered[9]` — **the slowest of the ten**. The 1,500 ms figure in
`docs/development/performance-baseline.md` is therefore not a 95th percentile in
any statistical sense; it is a maximum, and it is maximally sensitive to a single
cold call. The pre-change 9,978.5 ms and post-change 567.5 ms figures are both
that one call.

This is recorded as a finding about the measurement, not fixed here. The harness
is deliberately unchanged by this issue so that the before and after runs remain
comparable. Changing the sample count, discarding a first sample per operation,
or reporting a maximum honestly instead of calling it P95 all belong in their own
issue against `docs/development/performance-baseline.md`.

## 8. Proposed follow-up work, not done here

**The statement still collects 12.6× more deliveries than any published figure
needs.** The participant appears on 969 of the 12,240 materialised deliveries
(561 as striker, 408 as bowler); the remaining 11,271 are materialised only
because `acceptedEventCount` and `emptyStandardInningsIds` are fixture-level
facts about deliveries the participant never faced or bowled.

Issue #285's `participant-aggregates.repository.ts` avoids this entirely by
starting from the partial indexes `delivery_striker_idx` and
`delivery_bowler_idx`. Narrowing this statement the same way, and deriving the
two completeness fields separately, is worth roughly the remaining 40 ms of
`accepted_delivery` construction. It is a larger change with real semantic risk
and is deliberately out of scope for #410.
