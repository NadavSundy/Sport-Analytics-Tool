# Issue #289 representative-scale response-time baseline

## Scope and environment

This is the pre-optimisation baseline for the operations and targets defined in
`docs/development/performance-baseline.md`. It records measurements already made
against the repository's large, public cricket corpus, rather than fabricating a
new result. The corpus had **14,011 fixtures** and **3,207,109 deliveries**;
that exceeds the issue's hundreds-of-fixtures and hundreds-of-events-per-fixture
scale requirement.

The backend ran locally in Johannesburg against the team's shared hosted
development database in eu-west-2. Requests were loopback requests to the
backend, so browser/public-internet latency was excluded while backend-to-database
latency was included. No production secret, production endpoint, private data,
or authentication credential was used or recorded here.

## Recorded warm baseline

Each endpoint was requested three times with curl and `time_total`; the first
request is shown separately from subsequent requests. These figures are copied
from the contemporaneous Issue #105 evidence, whose measurement method and
environment are the authoritative source.

| Operation                                         | First request | Subsequent requests | Assessment against Issue #289 warm target |
| ------------------------------------------------- | ------------: | ------------------: | ----------------------------------------- |
| `GET /api/v1/fixtures?limit=50`                   |      1,366 ms |      189 ms; 192 ms | Meets 500 ms target when warm             |
| `GET /api/v1/fixtures/{id}/statistics`            |      2,428 ms |  2,339 ms; 2,389 ms | Does not meet 1,500 ms target             |
| `GET /api/v1/participants/{id}/fixtures?limit=50` |      3,735 ms |  2,386 ms; 2,469 ms | Does not meet 1,500 ms target             |
| `GET /api/v1/health`                              |          8 ms |                8 ms | Context only; not a database operation    |

The statistic and participant aggregate results establish a genuine baseline
gap before optimisation. The fixture list shows that a single-round-trip public
page was already within target once warm.

## Cold and idle-cache evidence

Issue #369 separately measured the connection-state effect. A freshly started
local backend's first database-backed request was 2,863 ms and its warm request
was 183 ms. Once that client had been established, first requests after ordinary
45-second idle periods were 201 ms, 184 ms, and 183 ms. This supports the
procedure's separation of startup cold observations from warm P95 samples.

These are not results from the fictional generator. They are retained to show
the prior realistic-scale baseline honestly. Future runs must use the #289
generator and measurement command, record their exact local environment, and
must not overwrite this historical evidence.
