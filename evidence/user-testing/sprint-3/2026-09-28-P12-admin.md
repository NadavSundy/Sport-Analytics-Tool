instantly after the correction; the status timeline on a batch; rejection reasons.

Response: Page load speed, or failing that, making it obvious a page is still
loading rather than broken.

Response: Not for the first task — the participant stated they would have given up
and contacted support. The submit-then-correct flow, yes.

   rather than broken. (`P12-F10`, `P12-F11`)

   (`P12-F01`)

   (`P12-F09`)

1. Correcting a delivery straight after submitting it.
2. Statistics updating instantly after a correction.
3. The status timeline on a batch.
4. Clear rejection reasons.

## Severity reasoning

**`P12-F01` — S1.** The protocol reserves S1 for a finding that prevents
completion of a core workflow or makes the tested functionality effectively
unusable. `COR-01`'s first half failed outright with no workaround available to
the participant, who concluded they could not fix their own mistakes and would
contact support. Correction of previously published data is the subject of the
whole #605 gate, so the affected workflow is core by definition. The correction
workspace is rendered at one place only,
`SubmissionPage.tsx:1363`, gated on `result.kind === 'accepted' && result.correctionContext`,
so it exists only in the page session that created the submission; `App.tsx`
defines no correction route and the navigation offers no entry.

**`P12-F02` — S2.** A major obstacle in an important workflow with a workaround:
the batch reference is shown once an entry is opened, so entries can be
distinguished by opening each in turn. The list label comes from
`BatchReportsPage.tsx:438`, `batch.source.fileName ?? 'Submission report'`, and
carries no date, reference or fixture, so uploads sharing a filename are
indistinguishable in the list. Not S1 because the information exists one click
away.

**`P12-F03` — S2.** Same band and for the same reason. Without run values the
participant could not have identified the wrong delivery even had an edit control
existed, so this compounds `P12-F01` rather than standing alone. A workaround
exists through the public event pages, which do carry runs.

**`P12-F04` — S2.** `GET /api/v1/submissions/events/{eventId}/history` is
implemented and returns requester, timestamp, reason and full before/after states,
but no frontend code calls it — a search for `/history` across `apps/frontend/src`
returns nothing. The interface tells the user their reason will be retained, which
is true, and then offers no way to see it. Not S1 because the audit record is
genuinely stored and retrievable by an operator; the failure is in exposure, not
retention. Raised above S3 because the participant framed it as an inability to
prove what they changed, which is an accountability concern rather than mere
inconvenience.

**`P12-F05` — S2.** The submission history lists batches only — `BatchReportsPage`
is built on `listBatches`, and a direct submission creates a `submission` row with
no batch. So an administrator's accepted direct submission is invisible in the one
place a user would look for it. Combined with `P12-F04` the participant had no
post-hoc evidence of their own action at all, which is why both sit at S2 rather
than S3.

**`P12-F06` — S2.** `overNumber` is bounded only by
`eventCoordinateSchema` — an integer 0 to 32,767 — with no relation to the
fixture's `ballsPerOver` or `scheduledOvers`, and no cricket rule in
`validateCricketBusinessRules` constrains it against the innings. A delivery in
over 900 of a twenty-over match is therefore accepted, published, and folded into
derived statistics with nothing questioning it. Rated S2 rather than S1 because
reaching it requires a privileged account supplying a deliberately out-of-range
value, so it is a missing guard rather than a defect encountered in normal use;
rated above S3 because the result is silently wrong published data in a system
whose correction path is itself hard to reach.

**`P12-F07` — S4.** Wording only. `runs.nonBoundary` is a real and necessary
contract field; the label does not explain it to a user who has not read the
contract. No task outcome depended on it.

**`P12-F08` — S3.** Significant unnecessary effort without preventing completion.
The deciding actor is rendered on the submitter-facing report
(`BatchReportsPage.tsx:182-188`, "Review: {decision} by {actor} on {date}") but
nowhere in `BatchReviewWorkspacePage`, which is where an administrator tracing a
submission goes. The information is reachable by a different route, which keeps it
out of S2.

**`P12-F09` — S2.** `ADM-02`'s second observation is whether the relationship
between submission, events and statistics is understandable. It is not navigable
in either direction: neither `BatchReportsPage` nor `BatchReviewWorkspacePage`
links to `/fixtures`, and no fixture, event or statistic page links back to a
submission. The participant traced provenance "halfway, but not all the way",
which is the definition of a major obstacle with a partial workaround.

**`P12-F10` — S1.** The participant twice described the site as appearing broken
and said they would have abandoned it. Judged on impact, a workflow a user
abandons is not completed. This is a deployed-environment finding rather than a
code-path finding — see the corroboration note below.

**`P12-F11` — S2.** A specific, fixable contributor to `P12-F10` rather than a
restatement of it. `listAllFixtures` (`submission-api.ts:54-74`) pages through
every fixture in the database sequentially, `limit=100`, following the cursor
until exhausted, then filters out those without a competition client-side. A
deployed fixture list reported 14,011 total records on 2026-09-18
(`totalPages` is `Math.ceil(totalRecords / limit)` and was 14,011 at `limit=1`),
which is about 141 sequential requests. At the #599 deployed P50 of 668 ms for a
public fixture page that is roughly 94 seconds, which matches the participant's
"about a minute" on the submission page closely enough to treat as the likely
cause. Recorded as S2 because a single scoped request would replace it.
