# ADR-011: Private Azure Blob Storage with PostgreSQL provenance

- **Status:** Accepted for Intermediate implementation
- **Date:** 2026-08-21
- **Participants:** Dean Feldman (document owner); Nadav Sundy (issue #356 approval)
- **Related issues:** #55, #356
- **Approval:** Nadav Sundy approved Azure Blob Storage and 90-day batch-source retention for issue
  #356 on 2026-09-02.

## Context

The platform needs to retain source uploads and generated dataset releases without placing large
binary objects in PostgreSQL. Azure App Service's local filesystem is a deployment detail rather
than shared durable storage. At the same time, a storage service must not bypass the handwritten API,
submission authorisation, validation, provenance, or deletion policy.

The current system accepts structured cricket data rather than arbitrary public media. Batch source
payloads use the approved 90-day retention period. Malware scanning, residency, recovery, and cost
remain provisioning checks rather than reasons to leave the provider choice unresolved.

## Decision

Use a general-purpose v2 **Azure Storage account with private Blob Storage containers** when retained
source bytes or generated exports outgrow bounded request processing. Access it only through a
backend-owned `ObjectStore` adapter used by the API and workers.

PostgreSQL remains authoritative for ownership, authorisation, lifecycle, and provenance. Blob
Storage holds bytes. A database object record contains the generated object ID, purpose, container
and blob key, byte length, media type, SHA-256 checksum, source/retrieval details, state, owner,
retention class, creation time, and any provider version ID. Domain rows reference that object ID,
not a user-supplied path or a bare public URL.

### Containers and object lifecycle

Use separate private containers or equivalent access boundaries for:

- `incoming`: newly uploaded, unavailable to importers until validation and any required scanning;
- `sources`: accepted immutable source artefacts linked to submissions and imported events; and
- `releases`: completed immutable dataset files and manifests.

Exact environment-prefixed resource names are deployment configuration. Blob keys are generated by
the server and include an environment, object purpose, creation partition, and opaque object ID.
User filenames are retained only as sanitised display metadata. Keys are never reused; a replacement
or correction creates a new object and database record.

The upload flow is:

1. Authenticate and authorise through the API; allow-list media type and extension and enforce
   compressed and expanded size limits.
2. Create a database object record in `pending` state with an opaque identifier.
3. Stream bytes to the `incoming` key while calculating SHA-256; do not buffer an unbounded file in
   application memory.
4. Verify byte count, checksum, structure, and malware policy before marking the object usable.
5. Promote by server-side copy to an immutable generated `sources` key, or delete/quarantine it on
   rejection; update database state transactionally around the observable transition.
6. Pass structured content through the same submission validation and review path as direct JSON.

Generated releases are written to attempt-specific keys by ADR-010 workers. A completed release is
made visible only after the file and manifest checksums, row counts, schema versions, source
provenance, and database state commit successfully.

### Access and protection

- Containers deny anonymous listing and access by default.
- The backend and worker use managed identity with least-privilege Azure RBAC where available. Do not
  store an account key in source control or browser configuration.
- Downloads flow through an authorised API endpoint. The endpoint may stream the blob or return a
  short-lived read-only user-delegation SAS for that single object. It never grants write, list, or
  container-wide access.
- Browser-to-Blob direct upload is deferred. If later measurements require it, the API may issue a
  short-lived write-only SAS for one preallocated incoming key and must verify the completed object
  before it becomes usable.
- Enable secure transfer, disallow public blob access and Shared Key access where platform
  integration permits, and restrict storage networking to the required services.
- Enable blob and container soft delete. Enable blob versioning for retained source and release data
  unless the approved cost model instead relies on unique immutable keys plus tested backup. Apply
  lifecycle rules to remove abandoned incoming objects, expired private exports, old versions, and
  soft-deleted data after their approved recovery windows.
- Use a time-based immutability policy only for release or evidence classes that have an approved
  write-once retention requirement. It is not a substitute for backup and is not applied blindly to
  deletable personal or unlicensed data.

Deletion is a stateful operation. The database first records the authorised lifecycle transition,
then a retryable worker deletes the blob and records completion. Legal, licence, audit, backup, and
privacy retention rules are resolved before enabling arbitrary uploads or public releases. Hashes
and minimum provenance may be retained after byte deletion only when the approved policy allows it.

Original batch source bytes remain private for 90 days from receipt and are then deleted through the
stateful operation above. Batch metadata, checksum, expanded items, validation results, review
decisions, and event provenance are retained after byte deletion so published figures remain
reproducible and attributable. A legal or licence hold may extend source-byte retention only through
an explicitly recorded authorised decision.

### Failure and reconciliation

- A database reference is never marked ready until its blob is durably present and verified.
- Abandoned pending uploads, orphan blobs, missing ready blobs, checksum mismatches, and failed
  deletions are detected by scheduled reconciliation.
- Storage unavailability fails only file-dependent operations. Health, historical database reads,
  and unrelated API routes remain available.
- Logs contain object IDs and safe state transitions, not SAS tokens, account keys, full user paths,
  or file contents.
- Metrics cover upload failures, scan/validation time, orphan count, deletion lag, stored bytes,
  operation count, egress, lifecycle actions, and estimated cost.

## Alternatives considered

### Store bytes in PostgreSQL `bytea`

Rejected for retained uploads and releases because large objects increase database storage, backup,
restore, connection, and query costs. Small transactional JSON payloads may remain in PostgreSQL
when measurements show that separate object storage adds no value.

### Azure App Service local filesystem

Rejected because it is tied to an application instance and deployment lifecycle, is not a shared
durable contract, and cannot safely support workers or scale-out.

### Supabase Storage

Rejected for the initial target because Azure Blob Storage matches the accepted application hosting
platform and keeps object access behind an explicit provider adapter. Selecting Supabase Storage
could also confuse the prohibition on frontend use of generated Supabase data endpoints. It remains
a viable future provider only if a cost/residency review preserves the handwritten-API boundary.

### Public Blob containers

Rejected because uploads, source files, and private exports have different authorisation and
retention requirements. Approved public releases can be exposed through a deliberate download path
or a separately reviewed public distribution boundary.

### Keep only parsed database rows

Rejected for sources where audit, reproducibility, licence, or reprocessing requires the exact
retrieved bytes and checksum. A retention decision may still delete raw bytes when those needs do not
justify their cost or privacy risk.

## Advantages

- Separates large-byte cost and scaling from authoritative relational queries.
- Fits the accepted Azure hosting direction while remaining behind a portable adapter.
- Generated keys, checksums, immutable promotion, and PostgreSQL metadata preserve provenance.
- Private containers and object-scoped short-lived access maintain the backend security boundary.
- Lifecycle, soft-delete, versioning, and reconciliation provide explicit recovery controls.

## Disadvantages and risks

- Adds a cloud resource, identity/RBAC, networking, lifecycle policy, monitoring, egress, and cost.
- Database and Blob Storage cannot share a transaction, so intermediate states and reconciliation
  are unavoidable.
- Malware scanning and archive-bomb protection require operational capability beyond extension or
  MIME checks.
- Versioning, soft delete, immutable retention, and abandoned multipart data can create unexpected
  storage charges.
- A leaked SAS grants its encoded access until expiry; permissions and lifetime must be minimal.
- Incorrect retention can either destroy required provenance or retain personal/licensed data too
  long.

## Consequences

- File-upload and export APIs refer to stable application object IDs, never provider keys.
- ADR-010 workers handle large imports, release generation, promotion, and retryable deletion.
- Schema migrations and Azure resources are introduced by the retained-file implementation issues.
  Scanning, residency, recovery and cost controls must be verified while provisioning.
- Backups and recovery exercises must cover both PostgreSQL metadata and Blob Storage; restoring one
  without reconciling the other is incomplete.
- A provider change does not alter domain records or public URLs because only the adapter resolves
  object locations.

## Verification and review date

The provider and batch-source retention decisions were accepted for Intermediate implementation
under issue #356 on 2026-09-02. Review again before large or public uploads are enabled and after a
recovery rehearsal.
Tests must cover size and type rejection, malicious filenames, compressed expansion limits,
checksum verification, duplicate bytes with distinct source revisions, interrupted uploads,
scan/validation failure, unauthorised access, SAS scope/expiry where used, immutable release
publication, deletion retry, orphan reconciliation, storage outage degradation, and restore.

Provisioning remains separate implementation work. Acceptance of this ADR does not claim that the
storage account, containers, managed identity, lifecycle rules, or reconciliation jobs are deployed.
