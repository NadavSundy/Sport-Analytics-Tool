# Sprint 1 Planning

**Sprint:** Sprint 1  
**Date:** 6 August 2026  
**Attendees:** Git Push Pray Team

## Sprint Goal

Deliver and demonstrate a working **Basic vertical slice** of the Sport Analytics Tool while establishing the technical, governance, deployment, testing and documentation foundations required for later sprints.

The target end-to-end workflow is:

```text
administrator approves submitter
        ↓
approved submitter signs in
        ↓
submitter sends T20 cricket delivery events
        ↓
backend verifies identity, role and permitted scope
        ↓
events are validated
        ↓
invalid events receive useful rejection messages
        ↓
valid events are stored with provenance
        ↓
statistics are derived from accepted events
        ↓
public users view fixtures, events and statistics
```

Public browsing must remain available without authentication. Authentication is required only for account-specific and authorised submission or administration functionality.

### Authentication Approval

Supabase Auth with Google OAuth is the team's selected and implemented authentication foundation.

The written lecturer approval currently recorded in the repository explicitly covers Supabase-hosted PostgreSQL but does not separately confirm Supabase Auth.

Any formal confirmation required for production use must therefore remain visible as an open compliance item.

### Authentication Terminology

Some earlier planning material and issue text may still refer to Firebase.

ADR-004 and the current architecture supersede the earlier Firebase direction.

### Database Dependencies

Event submission, provenance and statistic derivation depend on stable database entities, migrations and backend repository behaviour.

Database work must therefore be reviewed before dependent ingestion and statistic features are treated as complete.

### Event Contract Dependencies

The executable submission contract in #49 must remain consistent with the relational event model originating from #27 and the submission/provenance schema in #61.

The external submission contract and internal relational database schema serve different purposes and should not be treated as duplicate work.

### Testing

### CI

## Decisions

### Sport

The project will focus on **T20 cricket**.

Detailed professional competition scope, cricket terminology and required statistics are owned by #37.

### Architecture

The system will maintain separate frontend and backend applications.

The frontend will communicate with application data through the handwritten backend API rather than directly using a generated database API.

### Database

The project uses **Supabase-hosted PostgreSQL** as the managed PostgreSQL platform.

### Authentication

The current authentication architecture is:

```text
React frontend
      ↓
Supabase Auth
      ↓
Google OAuth
      ↓
Supabase access token
      ↓
handwritten Express API
      ↓
application account, role, approval and scope
```

Authentication and authorisation are separate responsibilities.

Supabase Auth establishes identity.

The Sport Analytics backend determines application permissions.

### Application Identity

Application users will be identified using the provider-neutral combination:

```text
(auth_provider, provider_subject)
```

This prevents competition, event and statistic data from becoming coupled to a particular authentication provider.

### Public Access

Public users will be able to browse supported competition, fixture, event and statistic information without signing in.

Authentication will be required for functions such as:

- account management;
- authorised event submission;
- submitter-specific functionality; and
- administration.

### Event Data

Delivery events are the authoritative source from which supported cricket statistics are derived.

Statistics must not become an independent conflicting source of truth.

### Provenance

Accepted event data must retain sufficient provenance to trace:

```text
statistic
    ↓
event
    ↓
submission
    ↓
submitter/source
```

### Project Management

The project will continue using the approved lightweight Scrumban methodology.

Gitea remains the authoritative source for issue state, assignment, milestones and Pull Request progress.

The repository will retain sprint-planning and other methodology evidence.

### Sprint Targets

The agreed delivery targets are:

```text
Sprint 1
Working Basic vertical slice

Sprint 2
Complete remaining Basic + Intermediate

Sprint 3
Complete Advanced functionality

Final Submission
Hardening, evidence, documentation and release
```

## Expected Sprint 1 Outcome

Sprint 1 will be considered successful when the team can demonstrate a coherent Basic path in which:

1. an administrator can manage an approved submitter and permitted scope;
2. the submitter can authenticate;
3. the backend can resolve the authenticated application account;
4. an approved submitter can submit valid T20 delivery data;
5. unauthorised or out-of-scope submissions are rejected;
6. invalid events receive useful validation feedback;
7. accepted events are persisted with provenance;
8. fixture statistics are derived from accepted events;
9. public event and statistic information can be retrieved without authentication;
10. the principal workflow is covered by automated tests;
11. frontend, backend and documentation deployment paths are verified; and
12. the implemented state is documented and reviewed.
