## Team-Identified Defects

The team also identified two product defects while reviewing the system during
the Sprint 1 marking process.

### Submitter Access Scope

The current submitter-access interface exposes fixtures rather than the
intended competition scope.

The team has decided that access should be requested for a competition so that
an approved submitter can subsequently submit supported new data within that
competition.

This is tracked by:

**#255 — Fix submitter access requests to use competition scope instead of
fixture scope**

### Re-requesting Submitter Access

The current access lifecycle does not provide an appropriate re-request path
after rejection or revocation.

The team has decided that:

- a rejected user may request access again;
- a revoked user may request access again;
- previous access history must be preserved;
- an administrator reviewing a request from a previously revoked user must be
  clearly shown that the user was previously revoked;
- pending duplicate requests remain prevented; and
- currently authorised users cannot create unnecessary duplicate requests.

This is tracked by:

**#256 — Allow rejected or revoked submitters to request access again and flag
previous revocations**

This behaviour is being treated as a team product/consistency decision and
does not require additional stakeholder clarification before implementation.

## Monorepo Tooling Decision

The marker recommended adding monorepo maintenance tooling.

The team has divided this into three focused pieces rather than creating one
large tooling issue.

### #257 — dependency-cruiser

dependency-cruiser will provide architecture-boundary validation for the
monorepo.

Its purpose is to:

- detect circular dependencies;
- protect intended frontend/backend/shared-contract boundaries;
- identify inappropriate cross-component imports; and
- provide automated validation of architectural dependencies.

This work is intentionally separated because configuring useful architecture
rules requires more judgement than simply installing a package.

dependency-cruiser does not require CI/CD to be operational and can provide
value through the normal local quality process immediately.

### #258 — Knip and syncpack

Knip and syncpack will provide lighter repository-hygiene checks.

Knip will identify unused dependencies, exports and files.

syncpack will identify inconsistent dependency versions across the npm
workspaces.

These tools also do not depend on CI/CD and can be implemented and used
locally immediately.

### #259 — CI/CD Integration

The monorepo validation tools will later be added to automated CI/CD
verification.

Issue #259 therefore depends on:

- #257 — dependency-cruiser; and
- #258 — Knip and syncpack.

These dependencies have been recorded in Gitea.

Unlike #257 and #258, #259 cannot be fully completed while the CI/CD
environment remains unavailable.

It should therefore remain `Blocked` until the required CI/CD dependency is
available.

Separating the issues means useful local monorepo validation can be completed
without being unnecessarily blocked by CI/CD.

## Sprint 2 Process Improvements

The Sprint 1 retrospective identified several process improvements that will be
applied during Sprint 2.

### Communicate Intended Work

Where overlap is possible, team members should briefly communicate which issue
they intend to begin before starting implementation.

This is intended to reduce duplicated work.

### Keep Issues Smaller and More Focused

Large pieces of work should be split where appropriate so that they are easier
to implement, test, review and merge.

Issue scope should not expand silently during implementation.

### Identify Dependencies Earlier

Frontend/backend, infrastructure and other technical dependencies should be
identified before dependent work begins.

Blocking foundational work should be prioritised where necessary.

### Test and Integrate Earlier

Relevant testing and integration should happen during feature development
rather than being left until the end of the sprint.

### Communicate Blockers Earlier

Environment, dependency and integration blockers should be communicated and
recorded as soon as they are identified.

### Improve Environment Consistency

Environment and deployment configuration should continue to be standardised
and documented so that contributors are working with consistent assumptions.

### Improve Pull Request Readiness

Pull Requests should remain focused and implementations should be tested as
completely as practical before review.
