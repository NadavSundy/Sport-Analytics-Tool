## Context

Sprint 2 has been closed and the agreed repository state has been preserved using
the annotated `sprint-2` tag.

The original Sprint 1 roadmap targeted completion of the full Advanced feature tier
during Sprint 3. That roadmap also explicitly required the Sprint 3 backlog to be
reviewed at Sprint 2 close-out using implementation evidence, stakeholder feedback,
performance findings, unresolved technical risk, updated requirements and available
team capacity before the work was converted into detailed Gitea issues.

That refinement has now taken place.

Sprint 2 produced substantial Basic and Intermediate functionality, but the final
review, retrospective, deployed testing and post-review technical audit identified
remaining correctness, workflow, usability, reproducibility and deployment work.

Sprint 3 therefore does **not** treat the project as a clean slate and does not commit
the team to the complete original Advanced backlog regardless of product state.

The active Sprint 3 plan prioritises:

1. completing and stabilising the Basic/Intermediate product;
2. addressing accepted Sprint 2 stakeholder/marker feedback;
3. strengthening testing, documentation and deployment evidence;
4. validating user-facing features through explicit feature-level user-feedback
   gates;
5. proving Basic/Intermediate end-to-end correctness through one formal acceptance
   gate; and
6. only then implementing a small set of selected Advanced API capabilities if
   capacity remains.

progressive refinement at Sprint boundaries.

## User-Feedback Gate Model

Sprint 2 showed that manually remembering which implementation issues had received
user validation was unreliable.

Sprint 3 therefore uses **feature-level user-feedback gates**.

Several technical issues may collectively deliver one user goal. Those implementation
issues are validated together through a dedicated user-feedback issue.

Implementation work may proceed while its feedback gate remains open, but a
user-facing implementation issue must remain open until its required feedback gate
has been completed.

Gitea issue dependencies provide the primary closure enforcement: an implementation
issue that depends on an open user-feedback gate cannot be closed.

Issue #600 extends the existing task bank, facilitator data and evidence process and
formalises this Sprint 3 gate workflow.

The team will continue using the existing task-based user-testing process:

- role-based tasks;
- no coaching while a task is active;
- `Success / Partial / Failure` per task;
- S1-S4 finding severity;
- Gitea-linked actionable findings;
- explicit accepted / deferred / rejected decisions;
- mandatory retest for accepted S1/S2 fixes; and
- committed anonymised evidence.

## Intermediate Acceptance Gate

**Issue:** #598
`test(acceptance): prove Basic and Intermediate end-to-end correctness on the deployed Sprint 3 build`

#598 is the formal Basic/Intermediate completion gate.

It does not implement missing functionality. Any failure found during acceptance must
be linked to an owning issue, corrected and retested.

The gate must prove, at minimum:

- genuinely new fixture submission through the normal application workflow;
- canonical onboarding and participant/context resolution;
- competition-scope enforcement;
- deterministic event/reference/sequence handling;
- multi-season back-catalogue ingestion;
- idempotent replay;
- correction history and stable logical event identity;
- correct fixture and aggregate statistics;
- selective recomputation;
- aggregate provenance;
- consumer key/quota/rate-limit controls;
- shared rate-limit behaviour for the deployed topology where feasible;
- versioned dataset release schema/checksum;
- coherent point-in-time release generation;
- derivation-complete release fields;
- representative-scale / production-scale acceptance; and
- completion of the required feature-level user-feedback gates.

The selected Advanced issues may only become active implementation priorities after
#598 passes.

## Initial Ownership

Detailed ownership is intentionally not invented in this planning document.

At the time of Sprint 3 planning, several newly created issues remain unassigned.
The first Sprint 3 team action is to assign owners according to availability,
technical context and dependency order.

Until that allocation is completed:

- unresolved ownership is explicit rather than hidden;
- no issue should move to `Ready` merely because it exists in the Sprint 3
  milestone;
- each issue should have one clear active owner before implementation begins; and
- parallel work should be distributed to avoid multiple people modifying the same
  high-conflict files unnecessarily.

The Gitea issue remains authoritative for the current assignee.

## Definition of Ready

Sprint 3 continues to use the project's Scrumban Definition of Ready.

For Sprint 3 specifically, an issue should not move to `Ready` unless:

- the purpose and acceptance criteria are clear;
- known technical dependencies are recorded;
- required test/evidence expectations are understood;
- the relevant user-feedback gate is identified where applicable;
- required environment/access prerequisites are available;
- an owner is assigned; and
- implementation can begin without unresolved scope ambiguity.

Selected Advanced issues additionally require #598 to have passed before becoming
active implementation priorities.

## Definition of Done

A Sprint 3 implementation issue is not Done merely because code has been written or a
Pull Request has merged.

Where applicable, Done requires:

- acceptance criteria satisfied;
- relevant automated tests passing;
- required documentation updated;
- Pull Request reviewed and merged;
- deployed verification completed;
- evidence recorded;
- linked defects resolved or explicitly dispositioned; and
- the required feature-level user-feedback gate closed.

Technical quality issues that do not represent a user-facing feature may use technical
validation rather than an artificial user-testing gate.
