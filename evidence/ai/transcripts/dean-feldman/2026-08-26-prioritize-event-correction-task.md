## Recommended next task: **#267 - Implement authorised event correction with automatic statistic refresh**

This is the one I would take next, assuming nobody else has already claimed it.

The main reason is that **event correction is part of the core architectural requirement of the Sport Analytics Tool**, not merely a nice frontend feature. The project brief explicitly says that correcting an event should be sufficient to bring **every statistic derived from that event back into line without manually re-entering totals**. `sport_analytics (1).pdf`

It is also exactly the kind of risky, cross-cutting work you want to discover problems with early. #267 touches the **API + database + event data + statistics derivation + authorisation**, so if there is a flaw in your current event/statistics architecture, this issue will reveal it now rather than close to Milestone 2.

### Why #267 before the Intermediate work

I would **not jump to #275-#287 yet**, despite those being more exciting.

Your Advanced-tier goal ultimately requires Basic + Intermediate + Advanced, but the brief defines the tiers cumulatively. Intermediate assumes the Basic functionality exists first. `project_briefs (4).pdf`

And #267 verifies several things you will later depend on for Intermediate:

**event revision → accepted event state → derived statistics → API output**

If that chain isn't reliable, then later issues like:

- #284 immutable correction history,
- #285 season/career aggregates,
- #286 selective recomputation,
- #287 golden reference correctness

will be built on unstable foundations.

### What #267 should prove when you're finished

Your implementation should ideally demonstrate something like:

`approved submitter → authorised correction request → validate corrected event → persist correction → statistics derive from corrected accepted event → API immediately exposes corrected statistics`

And importantly:

`unauthorised user → 401/403`

and:

`invalid correction → useful validation error + no partial data modification`

That directly supports the Basic requirement that events drive statistics and that submissions are controlled by approved submitters. `sport_analytics (1).pdf`

I would also make sure #267 contains automated API tests for at least:

- successful correction;
- statistics before vs after correction;
- correction actually changes the appropriate statistic;
- unrelated statistics remain correct;
- invalid event rejected;
- unauthenticated correction rejected;
- viewer rejected;
- approved submitter in scope accepted;
- submitter outside their scope rejected;
- admin behaviour, according to your documented authorisation rules;
- database failure doesn't leave partially updated state.

That gives you useful evidence toward the Milestone 2 **Automated Testing 10%** criterion rather than treating tests as something to bolt on later. `project_briefs (4).pdf`
